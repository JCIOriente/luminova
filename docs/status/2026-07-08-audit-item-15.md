## Sub-PR A — beacon hardening (SENSITIVE) — PR #145 `fix/beacon-hardening-15`

Three defensive fixes on the claims-sync trust boundary (audit rows 135/137/136).

- **onRoleWritten scan (row 135).** Was an unconditional full-members-collection scan on any built-in role write. Fixed with an early-return via `roleClaimsChanged()` (new pure `claims-sync/role-change.ts`) when nothing claims-relevant changed. **Deliberately NOT a `.limit()`** (the audit's literal suggestion) — a real permission change must still re-sync every affected member, so capping the scan would strand stale claims. The predicate compares exactly the fields claims resolution reads: `permissions` (as **sets**), active-status (`active`/`deletedAt`), `builtInKey`, and the `builtIn` flag.
- **getRolesByIds bound (row 137).** `roleIds` is Admin-writable but rules cap no size; the unbounded `getAll(...refs)` now batches in 300-ref chunks via a new `chunk()` util (also adopted by `resolveMembers`, removing a hand-rolled duplicate loop).
- **teamIds dedup (row 136).** `parseInitiativeWrite` dedups `roster.teamIds` via `Set`, matching `coDirectorIds`.

**Bugs caught during review (all fixed):**
- **permsEqual multiset bug** (3 independent code-review finders + security identification): the compare was array-length + one-directional subset, so a permission REVOCATION masked by a duplicate (`["read","manage"] → ["read","read"]`) read as *unchanged* → holders would keep the revoked claim. Now compares deduplicated sets. Regression test added.
- **builtIn flag omitted** from the change predicate (Angle B): a built-in role only contributes perms while `builtIn===true`; added to the compare + test.
- **builtInKey-removal mis-target** (firebase-functions-reviewer Low-2): stripping `builtInKey` from a built-in role fell to the roleIds filter and missed position-holders → they retained stale perms. Now scans all members when *either* before or after is built-in.
