# K4 `onMemberWritten` claims-sync trigger — manual emulator e2e

Controller-run checklist. Do NOT start the emulator from inside an agent run
(races the user's running emulators). Run against the Functions + Firestore +
Auth emulators with the beacon function loaded.

## Setup

1. Build/load beacon so `onMemberWritten` is registered, with emulators running
   (Auth :4030, Firestore :4010, Functions :4020).
2. Have two pre-provisioned Auth users with known uids:
   - `<adminUid>` whose custom claims include `"Admin"` in `roles`.
   - `<membershipUid>` whose custom claims include `"Membership"` (NOT `Admin`).
3. Have a target member that will receive a `uid` (the user whose claims we assert).

## Steps

1. **Seed a power-conferring cargo.** Write `positions/pos-pres`:
   ```json
   { "grants": ["Admin"], "category": "CEL", "term": null, "active": true, "deletedAt": null }
   ```

2. **Provision the target member** (e.g. via `provisionMemberLogin` or by writing a
   `uid` onto the member doc). Capture the target Auth `uid` → `<targetUid>`.
   The trigger fires on the `uid` write; with no positions it should settle the
   target's claims to `roles: ["Member"]`.

3. **Untrusted assigner (fail-closed).** Set the member's
   `positions.2026 = { "cargoId": "pos-pres", "comisionIds": [], "assignedBy": "<membershipUid>" }`.
   - Assert: `<targetUid>` custom claims `roles` do **NOT** include `"Admin"`
     (a non-Admin assigner cannot confer a power grant). Expect `["Member"]`.

4. **Trusted assigner.** Set
   `positions.2026 = { "cargoId": "pos-pres", "comisionIds": [], "assignedBy": "<adminUid>" }`.
   - Assert: `<targetUid>` custom claims `roles` now include `"Admin"`.

5. **Clear the cargo.** Set
   `positions.2026 = { "cargoId": null, "comisionIds": [], "assignedBy": "<adminUid>" }`
   (or remove the `2026` term).
   - Assert: roles fall back to `["Member"]`.

## Notes

- The trigger writes Auth custom claims, not the member doc, so it cannot
  retrigger itself. Idempotent: a no-change write produces no claims write.
- After updating claims, the target user must refresh their ID token for the new
  claims to take effect in the client.
- Year in `positions.<year>` must match `currentTermKey()` (UTC current year);
  swap `2026` for the current year if running in a later year.

## Known limitation — UTC term rollover

`currentTermKey()` (trigger), the member mapper, `firestore.rules` (`request.time.year()`), and the frontend all key the active term by **UTC calendar year**, matching the K2 design (term = calendar year, no gestión entity — see spec "Out of scope"). At the UTC New-Year boundary the active term advances to the new year; until that year's assignments are created, members have no current-term cargo and the trigger computes `['Member']` (org roles drop until reassigned for the new gestión). This is the intended yearly-board-reassignment workflow, not a defect. Revisit if a non-calendar gestión entity is ever introduced.
